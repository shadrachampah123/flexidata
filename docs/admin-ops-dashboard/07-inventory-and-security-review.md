## 4. Security review

### 4.1 Authentication & authorization — PASS

- **Every admin surface re-checks the gate.** `verify:admin-phase1` asserts 24 API routes and 17 pages all call `requireAdminApi()` / `requireAdmin()` first, before any input is read. `verify:admin-ops` adds the 6 investigation routes. No handler or page is ungated.
- **Two independent signals, re-evaluated every request.** `users.is_admin=true` (read fresh from DB) **AND** `ADMIN_EMAILS` allowlist. Compromising DB alone or env alone is insufficient. Tested via `verify:admin-access` (both-signals-required, revocation immediate).
- **Never in the cookie.** `fd_auth` carries only `uid/sid/exp` + HMAC; admin claim is resolved from `sessions.token_hash` + `users.is_admin`. Cookie decode verified not to leak admin.
- **No oracle.** Denials are 404 with byte-identical bodies/headers for anonymous, customer, forged, and non-allowlisted admin. `verify:admin-access` and every later harness prove byte-identical denial.
- **Test seam locked.** `FLEXIDATA_TEST_USER_ID` honoured only with `FLEXIDATA_TEST_ALLOW_ADMIN=1` + both admin signals + `NODE_ENV!=production`. Production ignores it unconditionally (proved live).
- **Fail-closed on degrade.** Driver-level faults (42703/42P01/57P01) deny access, never assume yes (`verify:admin-access` section 8).

**Gap acknowledged:** No per-role RBAC yet; all `is_admin` users have identical powers (suspend, support, withdrawal approve/reject, reconciliation). This matches the pre-Phase-3 scope and is documented as a blocker for distinct approver enforcement.

### 4.2 Role & permission boundaries — PARTIAL

- Current model is binary: `is_admin` flag. `admin_roles` / `admin_role_assignments` tables do not exist; `src/lib/admin/auth.ts` is the sole gate.
- Withdrawal admin path today enforces *customer requests, admin approves* but not *admin_A proposes, admin_B (different user) approves*. The harness does not yet assert `proposer≠approver`. This is the documented Phase 5 gap — keep it until `wallet_adjustments` with per-role caps lands.
- No step-up re-auth (password re-entry) on financial approve — planned for Phase 3. Current mitigation is explicit `confirm: true` + typed-ref + reason.

### 4.4 Input validation — PASS

- **Withdrawals:** `validateWithdrawalRequestBody` is pure, runs before any wallet TX; rejects missing/unknown keys (smuggling →400), non-strict `amount` (must be exact `parseCedisAmount` pesewas), method whitelist (`momo_mtn|telecel_cash`), destination strictly normalized via `normalizeGhanaMobileStrict` (no truncation, country-code handling, prefix checks), network must match method. `MAX_DEST_LENGTH 32`, `MAX_METHOD_LENGTH 40`, `IDEMPOTENCY_KEY_PATTERN ^[A-Za-z0-9_-]{8,64}$`. Tested exhaustively (81 + 213 checks).
- **Withdrawal admin action:** strict body `{action,reason}` only; `action` enum `approve|reject|refund|retry` else 400 (arbitrary status unreachable); `reason` trimmed, required for `reject`, ≤240 else 400 before TX; `id` must be positive int else 400; `status` never from client (derived via `ADMIN_WITHDRAWAL_ACTIONS`); terminal-withdrawal `retry`/`approve` →409.
- **Payout reconciliation:** `type` is filtered via enum, `resolved` boolean parsed, `page/pageSize` capped at 100, `note.slice(0,240)`, `exceptionId` validated as positive int.
- **Admin list filters:** `parseSearch` neutralises `%_*\\` wildcards, truncates to 60 chars; `parsePageSize` allows only [10,25,50,100]; `parseRef` enforces `[A-Za-z0-9_-]{4,40}`; every user input is a bound parameter (no SQL concatenation).

### 4.5 Audit logging — PASS (append-only for existing actions)

- **Every admin write is audited.** Customer suspend/activate → `admin_audit_logs` (adminUserId, targetUserId, action, reason, created_at) with FK `ON DELETE restrict`. Support `delivery_resolved`/`refund_review` → same table with `target_ref` + partial unique index. Withdrawal approve/reject/refund/retry → `admin_audit_logs` (target_ref = withdrawal ref, action `approve_withdrawal`/`reject_withdrawal`) **plus** `withdrawal_audit_logs` (previousStatus, newStatus, actorType, actorId, actorEmail, providerReference, reason) in the same TX as the money move.
- **No delete/update path.** No API deletes or modifies an audit row; schema has no `ON DELETE CASCADE` for `admin_audit_logs`. The harness asserts `admin_audit_logs` is in the immutable snapshot for read-only phases and that `verify:admin-ops` C10 proves exactly one row added per support action, no modification.
- **Before/after snapshot:** `verify:admin-phase1` F and `verify:admin-support` C7 prove financial tables byte-identical before/after the sweep.

### 4.6 Destructive actions & fail-closed — PASS
